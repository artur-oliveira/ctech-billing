# Realtime for CTech Billing (WebSocket, protobuf)

Status: **Draft for review** · 2026-10-14 · Repositories that change: `ctech-billing` (api, ui). Reused unchanged: `ctech-go-common` (`ws`, `drain`), `@aoctech/ws-client`. Plans: `docs/plans/2026-10-14-realtime-r1…r5-*.md`.

## 1. Intent

The system should be **driven by changes**. When something important is mutated, every connected client that has a relationship with it is told, and its screen corrects itself without a reload:

- a merchant looking at the invoice list or one invoice sees its status change when the payment arrives;
- a customer on the checkout page sees "pago" the moment the Pix settles;
- the portal, the console and Finanças (bills, statement, "a classificar", accounts) do the same.

Decisions taken with the owner (2026-10-14):

| | Decision |
|---|---|
| D1 | The transport is **WebSocket with binary protobuf**, built on what the Poker gateway and `ctech-go-common` already proved. |
| D2 | The protobuf contract is **Billing's alone** (`proto/realtime.proto` in `ctech-billing`). Wallet and DF-e are told through webhooks and do not use the socket, so no shared proto repository is created. Shared code stays what is already shared: `ctech-go-common/ws` (fan-out), `ctech-go-common/drain`, `@aoctech/ws-client` (it already takes `binaryType`, `encode`, `decode`). |
| D3 | An event carries **ids and state only** (what changed, which entity, its new status and revision), never personal or financial detail. The data itself keeps coming from the REST API, which already authorizes every read. |
| D4 | The checkout moves from Server-Sent Events to the socket in the first delivery. |

## 3. Principles

1. **The socket is a push optimisation over a cursor-based event log.** The log (an outbox written in the mutation's own transaction) is the truth; the socket only makes the common case instant. Everything else (a missed message, a reconnect, a blocked WebSocket) is answered by reading the log from a cursor, over the same code and the same authorization.
2. **An event is a hint to read, not data.** Receiving "invoice X is now PAID, revision 4" makes the client refetch X through the authorized API (or flip a badge, where the event alone is enough). A bug in routing can therefore at worst send a stranger an id and a status word, and the API still refuses the read.
3. **The server decides what a connection may hear.** Topics are derived from the verified token and the server-side membership, never named by the client.
4. **Nothing is lost silently.** Every loss path ends in either a replay or an explicit `Gap` that makes the client refetch.
5. **Flag off means today.** With the flag off, every screen behaves as it does now.

## 4. Architecture

```
mutation ──TransactWrite──▶ DynamoDB (row + audit + webhook Event + RT rows, one transaction)
    │ after commit
    ▼
Publisher ──▶ Valkey channel ws:<scope> ──▶ every instance ──▶ local connections of that scope
                                                         ▲
client ◀──── binary ServerFrame ─────────────────────────┘      replay: Query RT#<scope> > cursor
client ──── ClientFrame (auth, resume, ping) ──▶ Gateway   fallback: GET /v1.0/realtime/changes?cursor=
```

### 4.1 Scopes (who hears what)

A **scope** is an opaque key. Each change is written once per scope that should hear it; a connection is registered under exactly the scopes its principal is authorized for.

| Scope key | Heard by | Authorization |
|---|---|---|
| `tenant:{org}:{mode}` | the merchant's console | a console session whose resolved tenant is `org`/`mode` (same resolver as the REST routes) |
| `space:{spaceKey}` | Finanças of that space | membership of the space with `finance.read` |
| `user:{sub}` | the portal | the signed-in user; emitted for invoices/subscriptions whose customer has that `user_id` |
| `invoice:{org}:{mode}:{invoiceID}` | the checkout page of one invoice | the signed payment link (`PayLink`) for that invoice; nothing else |

The mode (`live`/`test`) is **part of every key**: test data can never be heard from a live scope.

### 4.2 The change log (outbox)

Written in the same `TransactWriteItems` as the mutation, so a change exists if and only if the mutation committed:

- `pk = RT#{scope}`, `sk = {event ULID}`, TTL 48 h, attributes: `type`, `entity`, `entity_id`, `status`, `revision`, `occurred_at`. One item per scope per change (at most four).
- Status transitions get it automatically from `buildEventWrites`' neighbour (`buildRealtimeWrites`, fed by the same `StatusChange.Emit`), so invoice, payment, subscription, checkout and credit-note changes need no new call site. Creation events and non-transition mutations (customer, bill, statement line posted, payer recorded, connection and payout state) call the same helper.
- The event ULID is the **cursor**. Replay reads `> cursor − 5 s` and the client drops duplicates by id: two instances' clocks can order events within a few milliseconds the wrong way round, and the overlap makes that harmless.
- Rows older than 48 h are gone. A client that has been away longer than that gets a `Gap` and refetches.

### 4.3 Publishing

After the transaction commits, the writer calls `Publisher.Publish(scope, frame)`, which `Broadcast`s on the existing `ws.Registry` (Valkey pub/sub). A publish failure never fails the mutation: it is counted and logged, and the log still has the change. Pub/sub is lossy by nature; the client's cursor and the periodic `Tick` (4.5) close that.

### 4.4 The gateway

`GET /v1.0/ws` upgrades to a WebSocket (Fiber + `fasthttp/websocket`, as the wallet and Poker do, on the same path). The cursor fallback stays under `/v1.0/realtime/changes`: it is a plain GET, not a socket.

1. **Auth first.** No credential on the URL. The first frame (5 s deadline, 32 KiB cap) is `Auth{token | pay_link, space?, resume_cursor?}`. Origin must be on the allow-list (missing Origin refused once an allow-list exists, as in the Poker gateway).
2. **Authorize and derive scopes** with the REST resolvers, once, then register under each scope key. The connection stores its principal and its `exp`.
3. **Ready** carries `protocol_version`, server time, and what was granted (scope *kinds*, not keys).
4. **Replay** `resume_cursor` before live frames: up to 500 changes; more, or a cursor older than the TTL, answers `Gap`.
5. **Steady state:** native ping every 30 s with a 45 s pong deadline; the app-level `Ping` of `@aoctech/ws-client` is answered with `Pong`; `Tick{head}` every 30 s.
6. **Re-authorization:** an in-band `Reauth{token}` swaps the token without reconnecting (the client sends it after a silent refresh). The server closes with `Bye{token_expired}` shortly after `exp` if none arrives. Membership is re-resolved every 5 minutes; removal closes with `Bye{revoked}`.
7. **Backpressure:** a bounded send queue per connection (256 frames). A full queue means a slow consumer: the connection is closed with a `Gap` hint so it reconnects and refetches. Writes are serialized per connection (fasthttp/websocket panics on concurrent writes).
8. **Limits:** 5 connections per principal, 30 per IP, 20 frames/s per connection, replay at most 3 per minute.
9. **Drain on deploy:** `ctech-go-common/drain` sends `Bye{draining}` and closes; clients reconnect with jitter and resume.

### 4.5 Protocol (`proto/realtime.proto`)

```proto
syntax = "proto3";
package ctech.billing.realtime.v1;

message ClientFrame {
  oneof body {
    Auth   auth   = 1;
    Reauth reauth = 2;
    Ping   ping   = 3;
  }
}
message Auth   { string token = 1; string pay_link = 2; string space = 3; string resume_cursor = 4; uint32 client_protocol_version = 5; string mode = 6; } // mode: "live" | "test" (empty is live); a selector, not a permission
message Reauth { string token = 1; }
message Ping   { uint64 client_time_ms = 1; }

message ServerFrame {
  oneof body {
    Ready  ready  = 1;
    Change change = 2;
    Gap    gap    = 3;
    Pong   pong   = 4;
    Tick   tick   = 5;
    Bye    bye    = 6;
    Hint   hint   = 7;
  }
}
message Ready  { uint32 protocol_version = 1; uint64 server_time_ms = 2; repeated string scope_kinds = 3; }
message Change {
  string id          = 1;  // ULID: the cursor
  string type        = 2;  // "invoice.paid": the webhook names, plus the realtime-only ones
  string entity      = 3;  // "invoice"
  string entity_id   = 4;
  string status      = 5;  // the entity's new status, when it has one
  uint64 revision    = 6;  // strictly increasing per entity: an older one is ignored
  uint64 occurred_at_ms = 7;
}
message Gap  { string reason = 1; }              // "cursor_too_old" | "slow_consumer" | "replay_limit"
message Pong { uint64 client_time_ms = 1; uint64 server_time_ms = 2; }
message Tick { string head = 1; }                // newest change id the server knows for this connection's scopes
message Bye  { string reason = 1; uint32 retry_after_ms = 2; }  // "token_expired" | "revoked" | "draining" | "limit"
message Hint { uint32 poll_interval_ms = 1; }    // the server asks the client to also poll (degraded fan-out)
```

Rules (enforced by CI, §7): field numbers are never reused (`reserved` on removal); additions are optional and old readers ignore them; a feature that a client must not use against an older server is gated on `Ready.protocol_version`, with each version written down in `docs/realtime/protocol.md` (the Poker `TableProtocolVersion` convention). There is no minimum client: an old client keeps working with new features dark.

Errors are not a frame type: an auth failure is `Bye` with a reason and a close code, so a client never has to tell "denied" from "not yet connected".

### 4.6 Fallbacks

`GET /v1.0/realtime/changes?cursor=…&limit=…` returns the same changes for the same scopes under the same authorization (a token or pay link in the `Authorization` header, never the URL). It is what replay uses internally, and what a client falls back to:

1. **WebSocket** (normal).
2. **Cursor polling** every 10 s while the tab is visible and the socket is down or `Hint.poll_interval_ms` is set (Valkey degraded, proxy blocking the upgrade, repeated failures).
3. **Refetch on focus + the existing slow `refetchInterval`** (what the screens do today). Never worse than the current behaviour.

### 4.7 The client

`useRealtime()` in `ui/src/lib/realtime/` owns one connection per tab (one per browser where Web Locks allow, others receive through a `BroadcastChannel`), the codec (generated `ts-proto`), the persisted cursor (`sessionStorage`, per scope kind), and the binding to TanStack Query:

- An event maps through a **catalogue** (`lib/realtime/catalogue.ts`): `entity + type → query keys to invalidate` and, where the event alone suffices (a status badge), a cache patch guarded by `revision`.
- Duplicates by id and out-of-order by `revision` are dropped. An echo of the user's own mutation is just an extra invalidate and is harmless.
- `Gap` invalidates every active query of the scope kind. `Bye{draining}` reconnects after jitter; `Bye{token_expired}` waits for the refreshed token; `Bye{revoked}` stops and shows the sign-in.
- Reconnect: backoff with jitter (`@aoctech/ws-client`), plus an immediate attempt on `online` and on the tab becoming visible; after N failures the fallback ladder takes over while reconnect attempts continue.
- A status indicator ("ao vivo" / "atualizando a cada 10 s") is shown only where it matters (checkout), never as a blocking state.

## 5. Security

| Risk | Control | Proof |
|---|---|---|
| User A hears user B's event | Scopes derived server-side from the verified principal; keys carry org, mode and entity; a change is written per scope | Table-driven isolation tests over every scope kind, with a randomized principal × event matrix asserting delivered ⊆ authorized (R2), and a two-tenant integration test through the real hub and registry (R5) |
| Test and live data mix | Mode in every key | Dedicated test: a `test` event never reaches a `live` connection and vice versa |
| Token on the URL (logs, history) | First-frame auth only; the polling fallback uses a header | Test: the upgrade request carries no credential; a connection with none is closed in 5 s |
| Cross-site socket hijack | Origin allow-list | Origin tests copied from the Poker gateway |
| A revoked member keeps listening | 5-minute re-resolution, `Bye{revoked}` | Integration test: remove the member, the connection closes |
| A long-lived socket outlives its token | `exp` tracked; `Reauth` or close | Test with a short-lived token |
| The event leaks data | Ids and state only (D3); no names, amounts, documents, Pix codes | A contract test lists the permitted field set of `Change`; adding a free-text field fails it |
| Checkout link abuse | The link authorizes only `invoice:{…}`; a cap per invoice | Test: a link for invoice 1 never receives invoice 2 |
| Resource exhaustion | Caps (§4.4.8), bounded queues, frame limit | Load test (R5) |

## 6. Failure modes

| Failure | Behaviour |
|---|---|
| An instance dies | Its clients reconnect (jitter) to another and resume from their cursor |
| Deploy | `Bye{draining}`, jittered reconnect, resume; no `Gap` expected |
| Valkey unavailable | Publishes fail (counted, alarmed); the gateway marks itself degraded and sends `Hint{poll_interval}`; clients poll the log; nothing is lost because the log is DynamoDB |
| A pub/sub message is lost | The next `Tick.head` is newer than the client's cursor → the client replays from the log |
| DynamoDB throttled | Replay answers `Gap{replay_limit}`; the client refetches through the REST API (itself throttled the same way) |
| Client offline for hours | Cursor older than 48 h → `Gap` → refetch |
| A browser blocks WebSocket | Fallback ladder step 2 |
| Event arrives before the REST read can see it | The REST read is strongly consistent for the entity the event names; the event is published after the commit |

## 7. Contract CI/CD (`proto.yml`)

Built on the Poker workflow (pinned generators, regenerate, fail on drift) and extended:

1. `buf lint` and `buf breaking --against '.git#branch=main'` on every change to `proto/**`. A breaking change fails the check; the only way through is a new message or a new field number.
2. Regenerate Go (`protoc-gen-go`, pinned) and TypeScript (`ts-proto`, pinned via `package-lock`) with `scripts/generate-proto.sh`, and `git diff --exit-code` on the generated files.
3. **Golden bytes:** `proto/testdata/*.bin` hold the encoding of a fixed set of frames. A Go test and a TypeScript test both decode every file and re-encode it to the same bytes. A change that makes either side disagree fails here, not in production.
4. The field-set test of `Change` (§5) runs with the Go tests.
5. The generated files are checked in; the API image and the UI build use them as they are (no generator at build time).
6. Deploy order for a protocol change: API first (it tolerates old clients), then the UI; `protocol_version` gates what the UI may use against an older server during a rolling deploy.
7. `docs/realtime/protocol.md` lists every `protocol_version` and what it added; a PR that changes `proto/**` must change it or state "no version change" in the template.

## 8. Observability

Per instance: connections (gauge, by principal kind), auth failures by reason, `Bye` by reason, frames sent, publish-to-write latency (from `occurred_at_ms` to the socket write, histogram), replays and their sizes, `Gap`s by reason, slow-consumer closes, Valkey publish errors, fallback-poll requests. Alarms (via the existing alerts topic): publish errors, p95 latency, `Gap` rate, connection count near the cap.

## 9. Rollout

`REALTIME_ENABLED` (api) and `NEXT_PUBLIC_REALTIME` (ui). Order: checkout (smallest surface, replaces SSE) → console invoices → portal → Finanças. A canary on one surface for a week with the SSE route kept; then the SSE route and `usePaymentStream` are removed. Rollback is the flag.

## 10. Cost

No new service. DynamoDB: up to four extra small items per mutation (TTL 48 h) and replay reads on reconnect; Valkey: the pub/sub it already runs. Connections are held by the existing instances. The first plan measures per-connection memory and the second sizes the instance cap; if the cap is hit the answer is another instance of the same ASG, not a new component.
