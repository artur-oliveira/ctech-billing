# Finance 6.3b — Console Screens (F1 basic, F2, F4, F8) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the finance backend of 6.2/6.3 in front of people: a **space switcher** (personal first, then organizations), and the four screens that phase promised — **F8** accounts, categories and settings; **F2** payables and receivables with settle/edit/cancel; **F4** recurrences with an expression editor that previews the next occurrences before saving; **F1** the finance overview (balances, overdue first, projection with virtual occurrences kept visibly apart).

**Architecture:** Same shell, same components, same patterns as the console that exists (`ui/src/app/(console)`, `@aoctech/ui`, TanStack Query, axios client, mock-mode transport). Two things are new and shape everything else: **the space is a request header and a segment of every query key** (exactly as the mode already is, PRODUCT.md), and **the console opens for everyone** — a signed-in person with no organization has a personal space and sees *Finanças*; invoices, subscriptions, customers and catalogue stay organization-only. A small backend slice comes first because the screens cannot be built without it (Part A).

**Tech Stack:** Next.js 16 static export (read `node_modules/next/dist/docs/` before writing routes — `ui/AGENTS.md` says this is *not* the Next you know), React 19, `@tanstack/react-query`, axios, `@aoctech/ui`, Tailwind 4, vitest + Testing Library; Go 1.27 for Part A.

**Spec:** [`docs/specs/2026-10-07-finance-erp-design.md`](../specs/2026-10-07-finance-erp-design.md) (§ 2, § 3.4–3.5, § 6, § 7, § 9 phase 3). Decisions: ADR 0023, 0024, 0025. Builds on [6.2](2026-10-07-finance-6.2-persistence-and-spaces.md) and [6.3](2026-10-07-finance-6.3-bills-and-recurrences.md).

## Scope decisions (read before executing)

1. **Part A is not optional and is not UI.** ADR 0025 and spec § 7 say the switcher lists organizations from ctech-account's `GET /v1.0/organizations`. That route is behind `RequireClientID(cfg.SelfClientID)` — *only account's own frontend* may call it (`ctech-account/api/cmd/api/main.go`, `adminAuth`) — so the billing UI's token gets a 403. The list therefore comes from billing: a new service route in ctech-account (`GET /v1.0/internal/users/:user_id/organizations`, the existing `internal:account:org-member` scope, which billing already holds) and `GET /v1.0/console/finance/spaces` in billing. The list is information for the switcher; **every request is still authorized by the resolver**, which is why the endpoint can be generous and the UI can be wrong without being dangerous.
2. **Space-unavailable must not look like maintenance.** `ui/src/lib/api/client.ts` sends *every* 503 to `/maintenance`. An organization space answers 503 `/problems/space-unavailable` when ctech-account is down, while the personal space works fine; redirecting the whole app would take the working half down with it. The interceptor learns that one problem type (Task 3).
3. **F1's "resultado realizado" is not here** (it ships with the cash read in 6.4; spec already says so). F1 shows what the API can state truthfully: balance per account, overdue first, the 3–6 month projection. No placeholder tile for the missing number.
4. **Layout and visual design are not decided in this plan.** The spec says it outright ("Visual design goes through `/impeccable` at implementation, on `@aoctech/ui`, in the console's compact density"), and DESIGN.md/PRODUCT.md already hold the constraints (sienna brand, restrained palette, compact density, plain Brazilian Portuguese, "show the derivation"). What this plan fixes instead is the **behaviour contract** of every component — props, states, copy that carries meaning, and the tests that pin them. Task 0 produces the design brief with the impeccable skill; Tasks 6–9 implement the contracts inside it. The projection chart goes through the `dataviz` skill.
5. **The OAuth scopes ship last and behind an operator step.** `ui/src/lib/auth/scopes.ts` documents that account *fails the whole sign-in* when the UI requests a scope the `billing` OAuth client was not granted. Adding `billing:finance:read|write` before the grant would break login for every user, portal included. Task 10 is a separate commit, and the plan states the order.

## Deploy order (the part that can break sign-in)

1. ctech-account: Task 1's route deployed.
2. billing API: Task 2 deployed (the screens' backend; nothing else depends on the UI yet).
3. **Operator:** grant `billing:finance:read` and `billing:finance:write` to the `billing` OAuth client at ctech-account (the same place its console scopes are granted — see the comment above `CONSOLE_SCOPES`). Confirm with a sign-in against the API's own scope manifest.
4. billing UI, including Task 10's scope change.

## Global Constraints

- UI code under `ui/`; run UI commands from `ui/`, Go commands from `api/` (and from `ctech-account/api/` for Task 1).
- **Money is integer centavos end to end.** No `parseFloat`, no `Number("1,5")`, no float arithmetic on an amount, in the UI either. Display goes through `money()` in `lib/format.ts`; input through the new `parseMoney` (Task 3).
- **Civil dates are `YYYY-MM-DD` strings** and are never passed through `new Date("YYYY-MM-DD")` (it reads UTC midnight and renders the day before west of Greenwich); use `lib/format.ts`'s `civil`-based helpers.
- **Every finance request carries `X-Billing-Mode` and `Billing-Space`**, added in the API module, never by a caller (the same rule the mode follows). **Every write carries an `Idempotency-Key`** that is stable across retries of one submit and fresh for the next.
- The space and the mode are segments of **every** finance query key.
- All user-facing copy is pt-BR, plain and exact; no internal names (`forecast`, `payable`, `OCCURRENCE`, problem types, ids) on screen — status and bucket enums are translated at the edge.
- Every screen has loading, empty, error and "your role does not allow this" states (assessment § 15); controls the role cannot use are **hidden**, and the server remains the authority.
- `@aoctech/ui` components only; no new dependency in `package.json` (Task 8's expression editor is built from existing controls).
- Static export: no server code, no dynamic route segments; a record is addressed by `?id=` on a fixed route, as `invoice/page.tsx` does.
- `npm run lint`, `npm test`, `npm run build` are clean before each commit. Commit messages carry no attribution trailer of any kind (user rule).

## Review Focus

1. **Wrong-space data on screen.** After switching space (or mode) no row from the previous one may render, and no mutation may go out under the previous one — Task 4 `TestEveryFinanceRequestCarriesTheSpaceAndModeHeaders`, `TestTheQueryKeysCarryTheSpaceAndTheMode`, `TestASwitchNeverRendersTheOtherSpacesRows`.
2. **A double click or a retry must not make two bills or two settlements** — Task 3 `TestAnIntentKeepsItsKeyAcrossRetriesAndChangesAfterSuccess`; Task 7 `TestSettleSubmitsOnceOnADoubleClick`.
3. **Money typed as "1.234,56", "0,05", "R$ 10", "1234.5" must become the right centavos or be refused — never a float's idea of them** — Task 3 `TestParseMoney`.
4. **A stored space that no longer exists (membership removed) must fall back to personal with a notice, not loop on 404s** — Task 4 `TestAStoredSpaceThatIsGoneFallsBackToPersonal`.

```go
// internalUserOrganizations lists the organizations a person belongs to, with
// their role in each, for a product that builds a space switcher (ctech-billing
// ADR 0025). It is information, not authorization: the product resolves every
// request's space through internalMember, so a stale or generous list cannot
// grant access.

// An unknown user answers an empty list rather than 404, for the reason the
// membership route does: asked about ids a caller may not be entitled to, a
// refusal must not reveal which exist.
func (h *OrganizationHandler) internalUserOrganizations(c fiber.Ctx) error {
	workspaces, err := h.svc.ListWorkspaces(c.Context(), c.Params("user_id"))
	if err != nil {
		return apierror.ServerError(c.Path()).WithCause(err).Send(c)
	}
	out := make([]fiber.Map, 0, len(workspaces))
	for _, w := range workspaces {
		out = append(out, fiber.Map{"id": w.ID, "display_name": w.DisplayName, "role": w.Role})
	}
	return c.JSON(fiber.Map{"organizations": out})
}
```

```json
{
  "spaces": [
    {"kind": "personal", "label": "Pessoal"},
    {"kind": "organization", "organization_id": "0190…", "label": "Acme LTDA", "role": "admin", "verbs": ["finance.read", "finance.write", "finance.settle", "finance.import", "finance.configure"]}
```

Rules: personal is always first and always present; `verbs` come from `space.VerbsForRole(role)`; an organization whose role maps to **no** verbs is omitted (the resolver would 404 it anyway); account failing makes `spaces` hold only the personal entry and `organizations_unavailable: true` (200, not 503 — the personal space works and the screen must say the rest is unavailable). type spaceDTO struct {
```go
	Kind           string   `json:"kind"`

	Label          string   `json:"label"`
	Role           string   `json:"role,omitempty"`
	Verbs          []string `json:"verbs"`

func (h *financeHandlers) listSpaces(c fiber.Ctx) error {
	sub := middleware.GetClaims(c).Sub // the ONLY identity input
	out := struct {
		Spaces                   []spaceDTO `json:"spaces"`
		OrganizationsUnavailable bool       `json:"organizations_unavailable"`
	}{Spaces: []spaceDTO{{Kind: "personal", Label: "Pessoal", Verbs: space.All.Names()}}}

	orgs, err := h.spaces.Organizations(c.Context(), sub)
	if err != nil {
		slog.Warn("finance: listing organizations failed", "error", err)
		out.OrganizationsUnavailable = true
		return c.JSON(out)
	}
	for _, o := range orgs {
		verbs := space.VerbsForRole(o.Role)
		if verbs == 0 {
			continue
		}
		out.Spaces = append(out.Spaces, spaceDTO{Kind: "organization", OrganizationID: o.ID, Label: o.DisplayName, Role: o.Role, Verbs: verbs.Names()})
	}
	return c.JSON(out)
}
```

`money.ts`:

```ts
/**
 * Brazilian money input -> integer centavos, without ever touching a float.
 * Accepts "1.234,56", "1234,56", "10", "R$ 10", "0,5". Refuses zero, negatives,
 * more than two decimals, mixed separators and anything past Number.MAX_SAFE_INTEGER.
 */
const MAX_CENTS = Number.MAX_SAFE_INTEGER

export function parseMoney(input: string): number | null {
  let s = input.trim().replace(/^R\$\s*/, "")
  if (s === "") return null
  // "1.234,56": dots are thousands separators only when a comma decimal or a
  // 3-digit group follows; a bare "1234.5" is NOT pt-BR and is refused rather
  // than guessed at (it could be 1234 reais 50 or a typo).
  const comma = s.indexOf(",")
  let whole: string
  let frac = ""
  if (comma >= 0) {
    if (s.indexOf(",", comma + 1) >= 0) return null
    whole = s.slice(0, comma)
    frac = s.slice(comma + 1)
  } else {
    whole = s
  }
  if (!/^\d{1,3}(\.\d{3})*$|^\d+$/.test(whole)) return null
  whole = whole.replaceAll(".", "")
  if (!/^\d{0,2}$/.test(frac)) return null
  const cents = BigInt(whole) * 100n + BigInt(frac.padEnd(2, "0") || "0")
  if (cents <= 0n || cents > BigInt(MAX_CENTS)) return null
  return Number(cents)
}

export function formatMoneyInput(cents: number): string {
  const whole = Math.trunc(cents / 100)
  const frac = String(cents % 100).padStart(2, "0")
  return `${whole},${frac}`
}
```
